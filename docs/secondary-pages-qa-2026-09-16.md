## Deleted-session Shop recovery

The reported slop_cosmetic_entitlements_user_id_fkey error was traced to the live database contract. The foreign key references auth.users(id), and my_slop_cosmetics() reads auth.uid() then calls entitlement synchronization before checking that the auth user still exists. An unexpired cached JWT can therefore reach that function after account deletion. No foreign key, entitlement policy, account row or grant was changed to work around the error.

Web startup now validates cached identity with GET /auth/v1/user before exposing authenticated account actions. Owner operations use the same authoritative check with a short 30-second cache; a 401/auth-JWT error or the exact reported entitlement foreign-key error forces fresh validation. Deleted or revoked sessions quarantine the app's private state and open a clear sign-in prompt. Automatic SDK logout is deliberately omitted: its delayed completion can erase a newer account and its PKCE verifier. Fresh sign-in replaces the rejected stored token; explicit user sign-out remains available. A network outage is shown separately and does not pretend that the stored session was valid. Validation also refreshes when returning to the page or reconnecting.

Eight focused tests cover server identity matching, deleted/expired users, no RPC before failed validation, exact FK recovery, preserving unrelated errors, account switches during validation, out-of-order auth events, teardown and outages. The complete web suite passed 70 tests; Auth JSX compiled with the project's Vite transformer. This evidence covers the code and live database diagnosis, not an invented new authenticated browser session after cleanup.

## Final auth and composer handoff regression

The final review removed automatic SDK sign-out from rejected-session recovery after inspecting the installed SDK's asynchronous logout followed by unconditional stored-session and PKCE-verifier removal. Recovery now changes only the invoking app snapshot. An old failed token cannot invalidate a newer token for the same account, and a delayed cached-session read cannot replace a newer auth event. Generic proxy errors, malformed error pages and invalid API-key responses are classified as service failures rather than missing users.

After an actual OAuth return and authoritative user verification, a valid pending pairing retains priority. Otherwise the validated, unexpired, owner-compatible awaitingAuth build idea restores its editor route. It never starts generation or consumes the idea. Email sign-in preserves the existing Build hash and idea ID; the existing owner-key remount restores the draft. Settings password-reset returns are excluded from this redirection. A later successful session check after an OAuth network interruption can still restore the handoff.

Thirteen session regression tests passed, including the additional refresh-token race, late cached read, gateway classification, failed-auth cache invalidation and pairing-versus-build return cases. The focused auth/owner/password run passed 28 tests; the complete web suite passed 86 tests, and Auth JSX compiled. No new QA account, OAuth authorization, generation or public post was created during this final regression review.
